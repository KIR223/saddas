# Развёртывание

## Локально

Корень репозитория — оба сервиса:

```bash
docker compose up --build
```

| Сервис | Контейнер | Порт на хосте | Содержание |
| --- | --- | --- | --- |
| backend | `melmk-backend` | `127.0.0.1:8000` | FastAPI, БД `/app/data/schedule.db` ← `./backend/data` |
| frontend | `melmk-frontend` | `127.0.0.1:8080` | nginx 1.27, volume `./frontend` read-only |

`ADMIN_TOKEN` берётся из окружения хоста, иначе `dev`.

Только API из папки `backend`:

```bash
cp .env.example .env   # необязательно
make migrate           # python -m app.migrate (идемпотентно)
make dev               # uvicorn --reload :8000
make test              # unittest discover tests
```

`uvicorn` сам вызывает `init_db()` при старте, отдельный `make migrate` нужен, когда схему поднимают без HTTP-процесса.

Либо `backend/docker-compose.yml` (сервис `api`, порт 8000, том `./data`).

Образ бэкенда: `backend/Dockerfile` — Python 3.12-slim, `uvicorn app.main:app --host 0.0.0.0 --port 8000`.

Публичный UI без Docker: `npx serve -l 8080 frontend` → `http://localhost:8080` и `/admin/`. Запросы всё равно идут на `API_ORIGIN`, пока не задан `window.SCHEDULE_API_BASE`.

## Продакшен

GitHub Actions `.github/workflows/deploy.yml` на push в `main`:

1. SSH (`DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_PASSWORD`).
2. Каталог `/opt/melmk-schedule`.
3. `git fetch origin main` → `checkout -B main` → `reset --hard origin/main`.
4. `docker compose up -d --build`.

Прод-API, на который зашит фронт: `https://api.melmksch.fvds.ru`. Менять URL в `frontend/js/api/config.js` только осознанно: клиенты ходят туда, а не на `:8080` контейнера nginx.

## Данные на диске

SQLite живёт в томе `./backend/data`. Пересборка контейнера файл не уничтожает.

Схема версионируется (`schema_migrations`). Старт API накатывает непрогнанные sql из `backend/app/migrations/versions/`. На проде после выкладки достаточно `docker compose up -d --build`; явно:

```bash
docker compose exec backend python -m app.migrate
```

Пустой файл и уже заполненный `schedule.db` без журнала миграций поднимаются одним запуском: `001_initial.sql` совпадает с прежней схемой и не затирает строки. Повтор команды ничего не меняет. Новые колонки и таблицы — только новым файлом миграции, не правкой `001_initial.sql`.
